# Screen2Social V0.3 — Social Package Design

Date: 2026-08-28
Status: approved design, implementation not started
Branch: `feat/v0.3-social-package`
Base: Screen2Social `0.2.0`

## Goal

Turn the existing deterministic media package into a minimally complete social publishing package for manual LinkedIn use.

V0.3 adds a local, deterministic `post.md` next to the already-generated media assets. It does not generate copy with AI, call social APIs, publish content, transcribe audio, edit silence, or introduce paid services.

The target package is:

```text
ready/<slug>/
├── linkedin.mp4
├── thumbnail.png
├── metadata.json
└── post.md
```

## Product principle

V0.3 should reduce the friction between "video processed" and "ready to publish manually" without creating a new subsystem.

The package itself is the unit of work. A user should be able to open one directory and find the final video, thumbnail, technical metadata, a place to write the post, and a publication checklist.

## Current baseline

Screen2Social 0.2.0 already provides:

- `screen2social process <video>`;
- deterministic `ready/<slug>/` package creation;
- `linkedin.mp4`;
- `thumbnail.png`;
- `metadata.json`;
- fail-closed behavior when `ready/<slug>/` already exists;
- source preservation and partial-package cleanup;
- OBS WebSocket `status`, `record`, and `stop` commands.

V0.3 must preserve those contracts.

## Scope

### In scope

1. Generate `post.md` during `screen2social process`.
2. Use one built-in LinkedIn-oriented Markdown template implemented with the Python standard library.
3. Formalize the existing `ready/<slug>/` naming as the canonical social package naming contract.
4. Include the canonical asset filenames inside `post.md`.
5. Include a small manual publishing checklist.
6. Add tests for template rendering, file creation, package completeness, cleanup, and naming behavior.
7. Update README documentation to reflect that V0.2 is complete and V0.3 adds the social package.

### Out of scope

- LLM-generated post copy;
- Whisper or any transcription;
- subtitles;
- silence removal or Auto-Editor;
- automatic `stop -> process` chaining;
- custom user template files;
- Jinja2 or another template dependency;
- platform-specific presets beyond the existing LinkedIn video asset;
- social-network APIs;
- browser automation;
- Postiz;
- scheduling;
- GUI;
- backend or database;
- automatic publication state tracking;
- changing the current OBS control surface.

## Package naming contract

V0.3 does not introduce a breaking directory rename.

The canonical package path remains:

```text
ready/<slug>/
```

`<slug>` continues to derive deterministically from the source recording stem through the existing `slugify()` behavior:

- Unicode normalized to ASCII where possible;
- non-alphanumeric runs become `-`;
- leading/trailing separators removed;
- lowercase;
- empty results fall back to `recording`.

Examples:

```text
"GeoPlatform Demo 01.mkv" -> ready/geoplatform-demo-01/
"Qué está pasando.mkv"    -> ready/que-esta-pasando/
```

Existing collision behavior remains fail-closed with `OUTPUT_EXISTS`. V0.3 will not append timestamps, counters, random IDs, or silently overwrite a package.

## `post.md` contract

`post.md` is deterministic UTF-8 Markdown generated from the source recording name and canonical asset names.

Initial template:

```markdown
# <human-readable title>

## Post

[Escribí acá el texto final del post]

## Assets

- Video: linkedin.mp4
- Thumbnail: thumbnail.png

## Checklist

- [ ] Revisé el video
- [ ] Elegí thumbnail
- [ ] Revisé el texto
- [ ] Publicado en LinkedIn
```

### Title behavior

The heading should use a readable form of the source stem, not the slug.

Minimal rule:

- use `source.stem.strip()`;
- if the stripped value is empty, use `Recording`;
- do not perform title-case rewriting;
- do not infer topics, brands, hashtags, handles, descriptions, or copy.

Example:

```text
source: GeoPlatform demo Filo del Sol.mkv
heading: # GeoPlatform demo Filo del Sol
```

## Architecture

V0.3 adds one focused module responsible only for social text-package rendering.

Proposed module:

```text
src/screen2social/social.py
```

Public responsibilities:

```python
def build_post_markdown(source: Path) -> str:
    ...


def write_post(path: Path, content: str) -> None:
    ...
```

`social.py` must not know about OBS, FFmpeg, CLI parsing, package directory creation, or publishing APIs.

`process_recording()` remains the orchestration point. After successful video transcode and thumbnail generation, it builds and writes `post.md` before the package is considered complete.

Expected flow:

```text
source recording
    -> create ready/<slug>/
    -> transcode linkedin.mp4
    -> probe output
    -> extract thumbnail.png
    -> write metadata.json
    -> write post.md
    -> return ProcessResult
```

`ProcessResult` should expose the new `post_path` so callers can reason about the complete package without reconstructing paths.

## Failure semantics

Existing atomic-ish package behavior must remain intact.

If writing `post.md` raises an `OSError` after the package directory has been created:

1. remove the newly-created partial package directory;
2. preserve the source recording;
3. surface the existing `PROCESSING_FAILED` domain error family;
4. do not leave `linkedin.mp4`, `thumbnail.png`, or `metadata.json` behind in a partial package.

No new error code is needed for V0.3 unless implementation reveals a materially distinct recoverable condition.

## Metadata

`metadata.json` remains technical pipeline metadata. V0.3 should update its `steps` value so it truthfully records the social-package generation step.

Expected steps after V0.3:

```json
[
  "linkedin_transcode",
  "thumbnail",
  "post_template"
]
```

Do not put editable post content into `metadata.json`.

## CLI behavior

No new command is required.

Existing command:

```text
screen2social process <video>
```

still returns:

```text
READY: <package_dir>
```

The only behavioral extension is that the returned package is now complete with `post.md`.

No prompt, interactive editor, `--post`, `--template`, `--title`, or `--platform` option is added in V0.3.

## Testing strategy

Implementation follows TDD.

### Unit tests

Add focused tests for `social.py`:

- source stem becomes heading without slugification;
- surrounding whitespace is trimmed;
- empty/whitespace-only stem falls back to `Recording` where constructible;
- output contains canonical asset names;
- checklist is deterministic;
- Markdown ends with a newline;
- UTF-8 content is preserved.

### Package integration tests

Extend package tests to assert:

- `post.md` exists;
- `ProcessResult.post_path` points to it;
- generated content references `linkedin.mp4` and `thumbnail.png`;
- `metadata.json.steps` contains `post_template`;
- source file remains untouched;
- a `write_post` `OSError` removes only the newly-created partial package;
- existing `OUTPUT_EXISTS` behavior remains unchanged.

### CLI regression

Existing `screen2social process` output stays unchanged. CLI tests should prove no extra stdout noise is introduced.

### Full regression

Run the complete existing test suite with FFmpeg available. V0.1 media and V0.2 OBS contracts must remain green.

## Versioning

Implementation work starts from package version `0.2.0`.

Do not bump runtime/package version merely to begin the feature branch. Once V0.3 passes tests, review, and the required real local smoke, perform the release identity bump to `0.3.0` at the release gate, keeping package metadata, `__version__`, and version-sensitive tests synchronized.

## Acceptance criteria

V0.3 is functionally complete when all of the following are true:

```text
process existing source                  PASS
linkedin.mp4 created                     PASS
thumbnail.png created                    PASS
metadata.json created                    PASS
post.md created                          PASS
post.md deterministic                    PASS
post.md references canonical assets      PASS
metadata includes post_template step     PASS
ProcessResult exposes post_path           PASS
source remains unchanged                 PASS
partial package cleanup on post failure  PASS
OUTPUT_EXISTS behavior unchanged         PASS
full automated suite                     PASS
GitHub Actions                           PASS
real Windows process smoke               PASS
```

A real OBS smoke does not need to revalidate WebSocket semantics unless OBS-related code changes. The V0.3 smoke can use either an existing real OBS-produced recording or a newly recorded one, then confirm the resulting four-file package.

## Explicit non-goals for the next implementation

Do not opportunistically add automatic copy generation, hashtags, multiple social platforms, template configuration, transcription, silence editing, `capture`, automatic chaining, or publishing.

V0.3 succeeds by making the existing package more useful, not by making the architecture larger.
